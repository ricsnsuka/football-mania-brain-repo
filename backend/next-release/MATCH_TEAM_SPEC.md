## 1. Overview

This specification defines the **Match** and **MatchTeam** entities, their relationships,
the schema changes required on top of V1, the API contract, validation rules, and DTO shapes.

The **Match** is the central aggregate. It owns two **MatchTeam** instances (home/away / team A/team B).
Each `MatchTeam` owns a list of **PlayerStat** records — one per player — which carry per-match
performance data (goals, assists, own goals, rating, MVP flag).

A separate **Goal** event table (already in V1) provides the fine-grained audit trail of every
goal event; `PlayerStat` stores the *aggregated* totals.

Maps to the existing `matches` table (V1) **plus** the new `match_type` column (V3 migration).

| Field            | Java type          | Column                | Nullable | Notes                                              |
|------------------|--------------------|-----------------------|----------|----------------------------------------------------|

| `matchType`      | `MatchType` (enum) | `match_type`          | No       | `FIVE_A_SIDE`, `SEVEN_A_SIDE`, `ELEVEN_A_SIDE`     |
| `isCompleted`    | `boolean`          | `is_completed`        | No       | Default `false`; `true` once score is recorded     |

| `teams`          | `List<MatchTeam>`  | —                     | No       | `@OneToMany`, always exactly 2 after creation      |
| `createdAt`      | `Instant`          | `created_at`          | No       | Set once on insert, immutable                      |
| `updatedAt`      | `Instant`          | `updated_at`          | No       | Updated on every `@PreUpdate`                      |

> **Season resolution rule:** `seasonId` is optional in `MatchCreateDTO`. When omitted (or `null`),
> `MatchService` fetches the season where `is_current = true` and assigns it automatically.
> If no active season exists and no `seasonId` was provided, a `BusinessException` is thrown.

#### MatchType enum

| Value           | Players per team |
|-----------------|------------------|
| `FIVE_A_SIDE`   | 5                |
| `SEVEN_A_SIDE`  | 7                |
| `ELEVEN_A_SIDE` | 11               |

#### GenerationType enum

| Value      | Meaning                                               |
|------------|-------------------------------------------------------|
| `BALANCED` | Teams generated by `CalculationService` (equal skill) — player count per team must match `matchType` |
| `MANUAL`   | Caller provides explicit player lists                 |

> **Note on `finalScore`:** V1 already has this as `VARCHAR(20)`.
> V3 migration will add `score_team_a` and `score_team_b` as separate integers (better for queries/rankings).
> `finalScore` will be derived and updated automatically as `"{scoreTeamA}-{scoreTeamB}"` by the service on completion.

### 2.4 Goal (event log — no Java entity change needed)

`Goal` is already fully specified in V1 and requires no structural changes.
It stores individual goal events and remains the **source of truth** for goal-by-goal replays.
`PlayerStat.goals`, `PlayerStat.assists`, and `PlayerStat.ownGoals` are derived aggregates.

| Column         | Notes                                               |
|----------------|-----------------------------------------------------|
| `is_own_goal`  | When `true`, the goal counts for the opposing team  |
| `is_penalty`   | Penalty kicks                                       |
| `assister_id`  | Nullable — direct shots need no assist              |
| `minute`       | 1–120                                               |

> ~~`penalty_caused_by`~~ — the `penalty_caused_by` column exists in V1 but is **not mapped** in the Java entity and is not exposed via the API. It will be dropped via V3 migration.

## 4. Schema Changes (V3 Migration)

> **V1 and V2 must not be modified.** All changes go in a new `V3__add_match_type_team_order_own_goals.sql`.

```sql
-- Add match_type to matches
ALTER TABLE matches
    ADD COLUMN match_type VARCHAR(20) NOT NULL DEFAULT 'SEVEN_A_SIDE'
        CHECK (match_type IN ('FIVE_A_SIDE', 'SEVEN_A_SIDE', 'ELEVEN_A_SIDE'));

-- Add separate score columns to matches
ALTER TABLE matches
    ADD COLUMN score_team_a INTEGER CHECK (score_team_a >= 0),
    ADD COLUMN score_team_b INTEGER CHECK (score_team_b >= 0);

-- Add team ordering to match_teams
ALTER TABLE match_teams
    ADD COLUMN team_order INTEGER NOT NULL DEFAULT 1
        CHECK (team_order IN (1, 2));

-- Unique constraint: each match has exactly one team_order=1 and one team_order=2
ALTER TABLE match_teams
    ADD CONSTRAINT uq_match_team_order UNIQUE (match_id, team_order);

-- Add own_goals to player_stats and drop notes
ALTER TABLE player_stats
    ADD COLUMN own_goals INTEGER NOT NULL DEFAULT 0
        CHECK (own_goals >= 0),
    DROP COLUMN notes;

-- Drop penalty_caused_by from goals (not used)
ALTER TABLE goals
    DROP COLUMN penalty_caused_by;

-- Indexes
CREATE INDEX idx_matches_match_type ON matches(match_type);
CREATE INDEX idx_matches_is_completed_season ON matches(is_completed, season_id);
```

## 5. Validation Rules

### 5.1 Match Creation

| Rule | Details |
|------|---------|
| **Team count** | Exactly 2 teams must be provided |
| **Team symmetry** | Both teams must have the **same number of players** |
| **Match type alignment** | Player count per team must match `matchType` (5, 7, or 11) |
| **No duplicate players** | A player ID must not appear in both teams |
| **Inactive players auto-activated** | If a player has `isActive = false`, the service **automatically sets `isActive = true`** before adding them to the team — no error is thrown |
| **Balanced constraint** | `generationType = BALANCED` → player count per team must equal the `matchType` value (5, 7, or 11) |
| **Season resolution** | If `seasonId` is not provided, resolve to the current active season (`is_current = true`). Throw `BusinessException` only if neither is available |
| **matchDate required** | `matchDate` must be present in the request |

### 5.2 Match Completion

| Rule | Details |
|------|---------|
| **Scores non-negative** | `scoreTeamA >= 0` and `scoreTeamB >= 0` |
| **Winning team valid** | `winningTeamId`, if set, must be one of the match's own team IDs |
| **Draw consistency** | If `scoreTeamA == scoreTeamB`, `winningTeamId` must be `null` |
| **No re-completion** | A match already marked `isCompleted = true` cannot be completed again (use the stat-amendment endpoint) |

### 5.3 Player Stats

| Rule | Details |
|------|---------|
| **Player in team** | Player must already have a `PlayerStat` record in the indicated team |
| **Rating range** | 0.0 – 10.0 when provided |
| **Single MVP** | At most one `isMvp = true` per match (across both teams) |
| **Stats amendment** | Once `isCompleted = true`, stats can only be amended via `PATCH /api/matches/{id}/teams/{teamId}/stats/{statId}` and only by `ADMIN_USER` |

## 9. Skill Rating Recalculation on Completion

When `completeMatch` is called, `CalculationService` must be invoked for each player to
update `Player.skillRating` and insert a `SkillRatingHistory` record.

> ⚠️ **The formula below is the original v1 model and has not been true since Rating Model v2.**
> It has no goal typing, no goal timing, no scarcity, and no match-wide normalization, all of
> which the service has done for two model versions. It is kept because this section documents
> *when* `CalculationService` is invoked, which is still accurate.
> **[CALCULATION_SERVICE.md](../features/CALCULATION_SERVICE.md) is canonical for the formula** —
> as of v2.2 goals and assists climb an escalating per-match ladder rather than carrying flat
> weights.

The formula (from project rules — **superseded**, see above):
```
matchRating = BASE_MATCH_RATING
            + (goals × GOAL_WEIGHT)
            + (assists × ASSIST_WEIGHT)
            - (ownGoals × OWN_GOAL_PENALTY)   ← own goals subtract from matchRating
            + WIN_BONUS          (if matchResult = WIN)
            - LOSS_PENALTY       (if matchResult = LOSS)
            + goalDiffBonus
```

Own goals are penalised — they reduce the player's `matchRating`. (Still true in v2.2.)

## 11. Resolved Decisions

| # | Question | Decision |
|---|----------|----------|
| 1 | Do own goals negatively affect `matchRating`? | **Yes** — deducted via `OWN_GOAL_PENALTY` constant |
| 2 | Is `matchDate` required? | **Yes — required** (`@NotNull` on DTO) |
| 3 | Does `BALANCED` accept all match types? | **Yes** — validates that player count matches `matchType` (5, 7, or 11) |
| 4 | Max teams per match? | **2 only** — enforced at service and DTO level (`@Size(min=2, max=2)`) |
| 5 | Can completed stats be amended? | **Yes** — `ADMIN_USER` only via `PATCH /api/matches/{id}/teams/{teamId}/stats/{statId}` |

## 13. Summary of Design Decisions

1. **`MatchTeam` is match-scoped** — never reused across matches.
2. **`PlayerStat` is the join** between `Player` and `MatchTeam` — carries all per-match player performance data (no free-text notes).
3. **`Goal` is an event log** — `PlayerStat` stores aggregated totals; goal events are for timeline/replay. `penalty_caused_by` is dropped.
4. **`team_order`** identifies which team is "A" (1) and which is "B" (2) — maps directly to `scoreTeamA`/`scoreTeamB`.
5. **`own_goals` added to `player_stats`** as an aggregate; they penalise the player's `matchRating`.
6. **Score stored twice** — as integers (`score_team_a`, `score_team_b`) for queries and as a derived string (`final_score = "3-2"`) for backward compatibility.
7. **Season is mandatory** — resolved automatically to the current active season when `seasonId` is omitted.
8. **Inactive players are auto-activated** on match creation — no error, silent state upgrade.
9. **Validation is service-layer** — team symmetry, match type alignment, and no-duplicate-player rules enforced in `MatchService.createMatch()` before any persistence.
10. **Stat amendments post-completion** are `ADMIN_USER`-only, handled by a dedicated PATCH endpoint.
